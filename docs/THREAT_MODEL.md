# Threat model

## Scope and security objective

PatchProof accepts candidate source diffs and executes the resulting case
tests. A candidate may be generated by a remote model or supplied directly by
a user. The objective is to reduce the chance that candidate code can affect
the host, reach external systems, access secrets, modify its tests, or consume
unbounded resources while producing evidence about the bundled local case.

The tool does not scan external targets and must not be used to test systems
without authorization. Vulnerable application snapshots exist only in `lab/`.

## Assets

- Host files, user credentials, API keys, Docker daemon, and other host
  workloads.
- Integrity of the case tests, reference implementation, and benchmark
  evidence.
- Availability of the host and CI runner.
- Confidentiality of any source placed in a provider prompt.
- Correctness of verdict and evidence attribution.

## Adversaries and untrusted inputs

- A malicious, malformed, or simply incorrect candidate diff.
- A prompt-injected or misleading source/test snippet embedded in model input.
- A buggy or compromised dependency, image, provider, or build action.
- A hostile test or candidate attempting network access, test modification,
  filesystem traversal, process spawning, or resource exhaustion.
- An operator who mistakenly exposes a deliberately vulnerable lab service.

The model provider is an external service. Its output is never trusted and is
not executed directly by the host process.

## Trust boundaries and controls

1. **Provider boundary:** only the vulnerable lab source, description, and
   visible tests are sent to Anthropic. Hidden tests, known patches, API keys,
   and host files are not intentionally included. API credentials are read
   from the process environment and are not passed to the sandbox.
2. **Diff validation boundary:** the validator requires one diff for exactly
   `source.ts`, rejects unsafe paths and structural changes, and caps patch
   bytes and changed lines. Application uses a strict no-fuzz patch operation.
3. **Execution boundary:** the candidate is mounted read-only as input, then
   copied and applied in the container's writable tmpfs workspace. The
   container is run with no network, read-only root filesystem, non-root UID,
   no added capabilities, `no-new-privileges`, bounded memory/CPU/PIDs, and
   per-test-stage timeouts.
4. **Evidence boundary:** the host parses a schema-checked runner response and
   writes evidence below `results/`. Hashes bind the recorded source and
   candidate text to that run. Evidence is not an attestation from a trusted
   remote execution service.
5. **CI boundary:** mock tests and benchmark require no secret. The real-model
   workflow is manual and exposes the API key only to the benchmark step.

The Docker image is built before a candidate patch is mounted. It contains
pinned project dependencies and the bundled tests; candidate code cannot
modify the image during a run. The default sandbox container does not receive
the Docker socket.

## Residual risks and limitations

- Containers share the host kernel. Docker or kernel vulnerabilities, a
  privileged/misconfigured daemon, or an unsafe host remain out of scope.
  Prefer disposable CI runners and do not run against a sensitive shared
  daemon.
- The sandbox runner and tests themselves are part of the trusted computing
  base. A malicious change to them, dependencies, Dockerfile, or CI workflow
  could invalidate the boundary.
- Docker limits reduce resource abuse but are not a formal guarantee against
  every denial-of-service condition; host-level quotas and runner timeouts
  still matter.
- The lab server binds to loopback and ephemeral ports. The vulnerable
  snapshots must never be deployed or exposed to a network.
- Anthropic receives the prompt contents over its API. Use only the bundled
  demo material; do not submit private or customer source.
- Hidden tests are withheld from the provider prompt, not kept secret from
  repository readers or a model with repository browsing access.
- A compromised provider response can still produce a misleading but
  syntactically valid patch. Independent tests reduce, but cannot eliminate,
  this risk.
- The filesystem evidence directory is user-writable. Consumers should not
  treat local evidence as tamper-proof or cryptographically signed.

## Safe use

Use only the bundled lab or software for which you have explicit
authorization. Do not point this tool at external targets. Do not deploy the
vulnerable lab cases. Do not use private source with the Anthropic provider.
Review code and evidence before making any security decision.
